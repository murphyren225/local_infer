# 路由策略

路由是 Tandem 的核心资产。模型谁都能换，**"这一步在哪跑、答砸了怎么办"的决策系统**才是长期积累的东西。

## 三层结构

| 层 | 时机 | 成本 | v0.1 状态 |
|---|---|---|---|
| Tier 1 启发式 | 生成前 | ~0ms | ✅ 已实现 |
| Tier 2 小模型预判 | 生成前 | 一次 4B 短推理 | 📋 规划 |
| Tier 3 升级兜底 | 小模型答完后 | 失败时一次 32B 推理 | ✅ 已实现 |

## Tier 1：启发式（`router/heuristics.py`）

硬规则（一票定车道）：

- 请求声明 `tools`/`functions` → large（4B 的函数调用不可靠）；
- 用户文本超过 `max_small_prompt_chars`（默认 6000 字符）→ large（小模型长上下文衰减最快）。

软信号（加权求和，`score >= large_threshold`（默认 3）→ large）：

| 信号 | 权重 | 说明 |
|---|---|---|
| 代码块 ``` | +2 | |
| 数学符号/证明类 | +2 | |
| 难任务关键词 | +2~+4 | 命中越多权重越高：1 个 +2，2 个 +3，3+ 个 +4。单个"分析"不该触发升级，"为什么+根因+分析"叠加才该 |
| 简单任务关键词 | -2 | 翻译/总结/分类/提取…… |
| 多问句（≥3 个问号） | +1 | |
| 较长文本（>2000 字符） | +1 | |
| 短文本（<200 字符且无难词） | -1 | |
| 长对话（>8 条消息） | +1 | |

设计原则：**每个决策必须可解释**。`Decision.signals` 保留完整信号明细，响应头 `x-tandem-reason` 带出，评测和线上排查都不用猜。

## Tier 2（规划）：小模型难度预判

启发式对"措辞平淡但实际很难"的请求会漏。Tier 2 用 4B 模型对灰区请求（score 在阈值 ±1 内）做一次难度自评（输出 1–5 分或 logprob 置信度），作为额外信号。

插入点已经留好：`policy.decide()` 是唯一决策入口，Tier 2 在 heuristic 评估之后追加信号即可，调用方不变。前提条件：积累足够的生产标注来评测它——**没有评测数据前不上线 Tier 2**，否则是在用一个没校准过的模型给另一个模型打分。

## Tier 3：升级兜底（`escalation.py`）

小模型答完后检查（仅非流式）：

- 输出为空 → `empty-output`
- 请求要求 `json_object` 但输出不是合法 JSON → `invalid-json`
- 输出命中不确定性词表 → `self-uncertain`

命中任一条 → 静默在 large 重答，响应头标 `x-tandem-escalated`。大模型也失败时保留小模型答案（可用性 > 完美）。

## 调参方法

1. 先跑基线：`python3 evals/run_evals.py --verbose` 看当前决策与信号；
2. 把你业务的高频词加进 `routing.extra_small_keywords` / `extra_large_keywords`（配置即可，不用改代码）；
3. 从生产日志挑误路由的请求，脱敏后补进 `evals/datasets/routing_eval.jsonl`；
4. 重跑评测，确认新增词没把别的类别改坏——这就是评测守门存在的意义。

监控哪个数说明路由歪了：

- `escalations` 高 → 小模型接了太多它接不住的活，调低阈值或补 large 关键词；
- large 车道请求占比远超 ~20% → 路由过于保守，白烧算力，补 small 关键词或调高阈值。
